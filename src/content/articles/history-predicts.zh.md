::scene overview

你机器上的每一条 [[tcp|TCP 连接]]，都在运行一个小小的预测循环。每收到一个[[ack|确认]]，发送方就量一下这次[[rtt|往返]]用了多久，把这个样本以八分之一的权重并入一个滚动的估计值，再据此设定一个定时器。如果定时器在下一个确认到来之前就触发了，TCP 便认定自己对网络的模型错了：它把定时器加倍，并把[[congestion-window|发送窗口]]砍到只剩一个[[tcp-segment|报文段]]，把它对这条路径能承载多少数据的认识丢掉了大半。

这个循环就是本文的全部思想：概括最近的过去，用它预测不久的将来，预测失败时就重置。第 8 章用 MLFQ 引出了这个思想，书中的旁注还点出了它的另外两个栖身之处——[[branch-predictor|分支预测器]]和缓存算法——并警告说这类技术“很容易出错”。本文沿着这个思想，走过这些系统以及另外几个。

::scene oracle

## 先知问题

::chapter cpu-sched-mlfq

第 7 章以一节“没有先知”（No More Oracle）收尾。SJF 和 STCF 能给出最好的平均周转时间，前提是调度器知道每个任务要运行多久，而通用操作系统并不知道。第 22 章在内存里撞上了同一堵墙：[[opt-policy|Belady 的最优策略]]淘汰将来最晚才会被用到的[[page|页]]，这同样需要预知未来。

两章给出的答案都是拿过去来顶替：MLFQ 观察一个任务过去的表现，[[lru|LRU]] 观察哪些页最近被用过。当负载存在*阶段*——在一段时间里，最近几毫秒的行为能说明接下来几毫秒——时，两者都很管用。

::scene parts

本文里的每一个基于历史的预测器都由三部分组成：

- **对过去的概括。** 小而且更新便宜：一个队列层级、一个平均值、一个两位计数器、一个窗口大小。
- **更新规则。** 每一次观察如何改变这个概括，旧的观察还保留多少权重。
- **遗忘的办法。** 一次重置、一种衰减或一个上限，用于概括已经过时、负载换了阶段，或者有人在钻规则空子的时候。

大部分工程功夫，最后都花在第三部分上。

::scene mlfq

## 作为预测器的 MLFQ

在 MLFQ 里，概括就是任务所在的队列层级，以及它在这一层已用掉的时间配额。更新规则是规则 4：用完配额就下降一层。于是任务的层级就是对它有多“吃 CPU”的一个滚动预测，起点是乐观的（规则 3）。

规则 5，即优先级提升，就是遗忘的办法：每过一段时间 S，所有预测一笔勾销。没有它，一个已经变成交互式的任务会一直待在底层，因为它的历史已经不再描述它；一群交互式任务也可能永远饿死一个长任务。

最终形式的规则 4 则保护预测器免受对手干扰：无论任务怎么切分自己的 CPU 使用，都照样扣配额，这样 CPU 大户就没法靠在时间片结束前一刻让出 CPU 来冒充交互式任务。

在实验里试试这些：

- 选 *+ 短任务*。B 被预测为短任务，在沉底之前就完成了：预测对的时候，MLFQ 的表现就像 SJF。
- 选 *饥饿*，先把提升设为 *从不*，再设为 50 ms。没有遗忘，A 的旧标签就把它一直压在底层。
- 选 *钻空子*，勾上 *更好的计时*：这条规则的改变，把一个可以被愚弄的概括变成了一个愚弄不了的概括。

## 一个会记忆的数：指数平均

MLFQ 的概括只是寥寥几个层级。另一种经典的 SJF 近似办法，为每个进程只记一个数，直接预测它下一次 [[cpu-burst|CPU 突发]]（burst）的长度，用的是**指数平均**：

> τ~n+1~ = α · t~n~ + (1 − α) · τ~n~

其中 t~n~ 是刚结束的那次突发的长度，τ~n~ 是当初对它的预测，0 到 1 之间的 α 决定最新样本有多大分量。取 α = 1/2，教科书里的经典例子从猜测值 10 出发，先后遇到 6、4、6、4，然后连续几次 13：

| 第 n 次突发 | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| 实际长度 t~n~ | 6 | 4 | 6 | 4 | 13 | 13 | 13 |
| 预测值 τ~n~ | 10 | 8 | 6 | 6 | 5 | 9 | 11 |

当进程切换到 13 个单位的突发时，预测一开始错了 8，然后去追新的值，每一步把误差减半：9、11、12。这一路追赶，就是预测器在遗忘。没有人去重置它，旧样本只是按几何级数失去权重。

它的代价是一个存储的数加每次更新一次乘加，这就是它在真实内核里随处可见的原因：

- **传统的 BSD 调度器**，也就是本书引用的[[decay-usage|衰减使用]]（decay-usage）设计，如今仍以 `sched_4bsd` 的形式留在 FreeBSD 里。它为每个进程记一个近期 CPU 使用量的估计，每秒乘以一次 (2 · [[load-average|load]]) / (2 · load + 1)。按源码注释的说法，目标是在 5 × loadavg 秒内忘掉其中的 90%，所以负载越重，它记得越久。
- **Linux 的[[pelt|按实体负载跟踪]]**（per-entity load tracking，PELT，3.8 合入）把时间看作一个个 1,024 µs 的周期，每个周期把累计负载乘以 y，其中 y^32^ = 0.5，于是 32 ms 之前的负载，分量只有现在的一半。
- **Linux 的 `util_est`** 为每个任务记一个指数平均值，在每次活跃期结束时用该期的利用率更新，新样本权重为 1/4。它为 [[dvfs|CPU 频率选择]]和任务放置提供输入，还有一个转折，见下文。

:::fold 遗忘的算术
把递推式展开，权重就露出来了。预测值是所有过去突发的加权和：

τ~n+1~ = α t~n~ + α(1 − α) t~n−1~ + α(1 − α)^2^ t~n−2~ + … + (1 − α)^n+1^ τ~0~

k 步之前的样本，权重是 α(1 − α)^k^。它永远不会归零，所以更有用的度量是**半衰期**：过多少次更新之后，一个样本的分量只剩新样本的一半，即 ln 2 / ln(1 / (1 − α))。α = 1/2 时是一次更新；`util_est` 的 1/4 约为 2.4 次；TCP 的 1/8 约为 5.2 次。

BSD 的数字也能这样核对。负载为 1 时，衰减因子是每秒 2/3，要只剩 10%，需要 n = ln 10 / ln 1.5 ≈ 5.68 秒，正是 FreeBSD 源码注释里列出的值。负载为 2 时约为 10.3 秒。PELT 的因子是 y = 0.5^1/32^ ≈ 0.9786。

`util_est` 让更新变得不对称。内核注释说：利用率上升时直接重置 EWMA，移动平均只用来平滑下降。用简化的伪代码表示：

```c
/* 伪代码，简化自 kernel/sched/fair.c（6.12）中的 util_est_update() */
void util_est_update(struct task *p, unsigned long dequeued /* 刚结束那次活跃期的利用率 */)
{
    unsigned long ewma = p->util_est;

    if (dequeued >= ewma) {              /* 任务变大了：立刻相信 */
        p->util_est = dequeued;
        return;
    }
    if (ewma - dequeued < UTIL_EST_MARGIN)
        return;                          /* 相差不到约 1%：不值得写回 */
    p->util_est = ewma - (ewma - dequeued) / 4;   /* = 3/4 * ewma + 1/4 * dequeued */
}
```

原因在于犯错的代价。任务变大而估计滞后，CPU 频率就定得太低，任务会卡顿；任务变小而估计滞后，CPU 只是在几次活跃期里跑得快了点，浪费一些电。所以预测器在一个方向上立即遗忘，在另一个方向上慢慢遗忘。
:::

## TCP：会学习的定时器，会重置的窗口

TCP 要对一条它看不见的路径猜两件事：一次往返要多久，以及路径上能同时容纳多少在途数据。

对往返时间的猜测驱动着**重传超时**（retransmission timeout，RTO）。[[rfc|RFC 6298]] 精确规定了这个预测器：发送方维护平滑往返时间 SRTT 和平滑平均偏差 RTTVAR，每来一个样本，就以 β = 1/4 的权重更新 RTTVAR、以 α = 1/8 的权重更新 SRTT，并令 RTO = SRTT + max(G, 4 · RTTVAR)，其中 G 是时钟粒度。RFC 说结果应当向上取整到至少 1 秒；Linux 默认用 200 ms 作下限（`tcp_rto_min_us`）。偏差项让它成为一个预测器，而不只是一个平均值：抖动大的路径得到的定时器远高于均值，这样一个慢了但没丢的包就不会触发多余的重传。

有两条规则专门处理“猜错了”。RFC 6298 强制要求的 **Karn 算法**规定：不从重传过的报文段采集 RTT 样本——一个段发了两次，就无从知道确认回应的是哪一份，这样的样本有毒。而定时器一旦触发，发送方必须**退避**：每超时一次，RTO 加倍。一个刚刚失败的预测，不被信任去设定下一个定时器。

:::fold 手算一次 RTO 更新
设一条连接已稳定在 SRTT = 100 ms、RTTVAR = 10 ms，于是 RTO 为 100 + 4 × 10 = 140 ms（Linux 会把它抬到 200 ms 的下限）。这时来了一个 R = 180 ms 的样本，也许是路径上某处正在积压队列。RFC 6298 先用旧的 SRTT 更新 RTTVAR：

RTTVAR = (3/4) × 10 + (1/4) × |100 − 180| = 7.5 + 20 = 27.5 ms

SRTT = (7/8) × 100 + (1/8) × 180 = 87.5 + 22.5 = 110 ms

RTO = 110 + 4 × 27.5 = 220 ms

均值只动了 10 ms，超时却动了 80 ms：一个出人意料的样本让偏差估计几乎翻了三倍，而偏差要乘以四。和 `util_est` 一样，这个定时器对坏消息的反应远快于对缓慢漂移的反应，因为过早触发的定时器会把没丢的数据重发到一条可能已经拥塞的路径上。
:::

::scene cwnd

对容量的猜测是**拥塞窗口**。按 RFC 5681，一切顺利时它每个往返大约增长一个报文段，因重复确认而发现丢包时大致减半：这是从“没有丢包”中学来的、变化缓慢的容量估计。一次重传超时则被当作模型错得离谱的证据：窗口降到一个满尺寸报文段的*丢失窗口*（loss window），重新开始[[slow-start|慢启动]]。

TCP 还会按计划遗忘。RFC 5681 第 4.1 节规定：一条连接空闲超过 RTO 之后，再次发送前应把窗口降到不超过初始窗口，因为 [[ack-clock|ACK 时钟]]已经停了，网络也可能变了。Linux 默认就这样做（`tcp_slow_start_after_idle`）。一条在两次页面加载之间停顿的持久 HTTP 连接，会小心翼翼地重新起步，因为它的历史被视为过时了。

::scene bbr

[[bbr|BBR]] 把遗忘做成了显式的。它的模型是两个经过滤波的测量值：近期投递速率的窗口最大值，以及过去 10 秒内 RTT 样本的窗口最小值。可只有在没有积压队列时，RTT 样本才能反映真实的传播时延，而一个忙碌的发送方总会维持一个队列。所以当最小值有一阵子没被刷新时，BBR 就进入 *ProbeRTT* 状态，把在途数据压低至少 200 ms，让队列排空，再重新测量。这就是定时执行的规则 5。

::scene branch

## 分支预测器：刻在硅片里的历史

[[pipeline|流水线]] CPU 在知道条件分支往哪边走之前很久就要取指令，所以它只能猜；猜错了，就要扔掉沿错误路径取来的工作。这是本文里约束最紧的历史预测：每隔几条指令就要做一次决定，每个分支只有几位状态。

James E. Smith 在 1981 年研究过的经典积木，是**两位饱和计数器**：它在 0 到 3 之间计数，分支跳转就加一，不跳转就减一，处于 2 和 3 时预测“跳转”。多出来的那一位换来了**迟滞**（hysteresis）。设想一个十次迭代的循环被反复执行：一位预测器每轮循环猜错两次——出口一次，下一轮入口又一次，因为出口把它翻了过去；两位计数器只是被出口削弱了一下，仍能猜对下一轮的入口，所以每轮只错一次。

后来的预测器扩大了概括。Scott McFarling 的 gshare 用分支地址与最近若干次分支结果做异或来索引计数器表，让同一个分支在不同上下文里学到不同的行为。André Seznec 和 Pierre Michaud 在 2006 年提出的 TAGE 维护几张表，分别用长度呈几何级数增长的历史来索引，并信任能匹配上的最长那一段。每个表项有一个 *useful* 计数器保护它不被替换，而这些计数器会被定期重置——用一篇综述的话说，免得表项永远被标记为有用。即便是用逻辑门搭出来的预测器，也需要规则 5。

:::fold 愚弄预测器：Spectre 第 2 变种
::scene spectre

MLFQ 的“钻空子”问题在硬件里有个孪生兄弟。分支预测器是共享状态：它从最近在这个核心上跑过的任何代码中学习，而且基本不记录那是谁的代码。

在 [[spectre|Spectre 第 2 变种]]，即*分支目标注入*（branch target injection）中，攻击者故意训练[[indirect-branch|间接分支]]的预测。Linux 内核文档把它描述为毒化[[btb|分支目标缓冲区]]（BTB），让受害者的间接分支在推测执行时跳到攻击者选定的代码上。推测执行的结果会被丢弃，但它在[[cpu-cache|缓存]]里留下的痕迹可能泄露数据。这就是第 8 章那种钻空子的威胁——向基于历史的预测器喂误导性的历史——只是目标从 CPU 份额换成了机密。

缓解手段之一就是重置。在 x86 上，**间接分支预测屏障**（Indirect Branch Prediction Barrier，IBPB）会清空分支目标缓冲区，让在一个上下文里学到的预测无法操纵另一个上下文；Linux 按启动时选定的策略在上下文切换时发出它。和 MLFQ 里更好的计时一样，目的都是不让一方的历史决定另一方的待遇。
:::

## 缓存与预取器

第 22 章是这个故事的内存版。LRU 预测最近用过的页很快会再被用到，[近似 LRU 那篇](/notes/approx-lru) 讲了真实系统如何连这个预测都要廉价地近似。再看两个例子，图景就完整了。

**频率比新近度更需要遗忘。** 没有老化机制的 [[lfu|LFU]] 缓存，会把一小时前热门过的页永远留着——这是反过来的饥饿——所以实用的 LFU 变体都会让计数衰减。Nimrod Megiddo 和 Dharmendra Modha 在 FAST 2003 上提出的 ARC 更进一步：它用一个链表记最近只见过一次的页，另一个链表记见过不止一次的页，还记住最近从两边各淘汰了哪些页。在一个刚被扔掉的页上未命中，说明两个链表之间的划分错了，它就相应地挪动空间。论文称之为一条不断修正其负载假设的学习规则。一次性的顺序扫描会直接穿过，而不会冲掉整个缓存。

::scene readahead

**预取是有预算的预测。** Linux 的预读（readahead）监视每个打开的文件是否在顺序访问。第一次读取时设定一个初始窗口，为请求大小的两倍或四倍，向上取到 2 的幂，并以最大值为限，常见的最大值是 128 KB。模式每保持一次，下一个窗口就放大，通常翻倍。一个孤立的小随机读按原样处理，用源码的话说，不会“污染”预读状态。当一个顺序流未命中、重新开始时，窗口也从初始大小重新开始。窗口就是预测，重新开始就是重置。

::scene arc

下面的实验是第 22 章的替换策略模拟器。选 *80-20*，大部分访问落在少数几个页上：历史派上用场，LRU 接近 OPT。再选 *循环访问*，用五个帧循环访问六个页：LRU 次次未命中，RANDOM 反而更好，因为最近的过去恰好完美地预测了错误的东西。ARC 多出来的那些链表，就是为了察觉这种情形。

## 押错的时候

基于历史的预测，总以三种方式失败，而上面的系统各自长出了对付每一种的办法：

1. **负载换了阶段。** 对策：衰减（指数平均、PELT），周期性重置（MLFQ 的提升、TAGE、ProbeRTT），以及在代价高的方向上快速反应（`util_est`、TCP 的偏差项）。
2. **有人钻规则空子。** 对策：躲不掉的计账（MLFQ 的规则 4），拒绝含糊的样本（Karn 算法），以及清空共享的历史（IBPB）。
3. **历史过时了。** 对策：显式过期，例如 TCP 空闲后的重新起步，或者 [真实调度器那篇](/notes/real-schedulers) 里 ULE 对睡眠与运行时间记忆设下的 5 秒上限。

整个模式可以装进一张表：

| 系统 | 对过去的概括 | 更新规则 | 如何遗忘 |
|---|---|---|---|
| MLFQ | 队列层级、已用配额 | 用完配额就降级 | 每隔 S 提升优先级 |
| BSD 调度器（`sched_4bsd`） | 衰减后的 CPU 使用量 | 每秒乘以 (2 · load) / (2 · load + 1) | 衰减本身 |
| Linux `util_est` | 利用率的 EWMA | 下降时权重 1/4 | 上升时立即重置 |
| TCP RTO | SRTT 与 RTTVAR | 权重 1/8 与 1/4 | 超时退避；Karn 规则 |
| TCP 拥塞窗口 | cwnd | 每个往返增长，丢包大致减半 | 超时后降到一个报文段；空闲后重新起步 |
| BBR | 最大带宽、最小 RTT | 窗口滤波器 | ProbeRTT 刷新 |
| 两位计数器 | 状态 0 到 3 | 跳转加一，不跳减一 | 饱和限制了记忆 |
| TAGE | 带标签的表、useful 计数器 | 最长匹配历史胜出 | 定期重置 useful 计数器 |
| ARC | 两个链表加淘汰页的历史 | 向“淘汰错了”的那一边挪空间 | 链表长度有界 |
| Linux 预读 | 每个文件的窗口大小 | 顺序时放大 | 从初始窗口重新开始 |

## 回到书里的那条线

第 7 章提出了问题：最好的策略需要一个先知。第 8 章用 MLFQ 为 CPU 作答，又因为答案会过时而加上了提升。第 9 章的 [EEVDF 那篇](/notes/eevdf) 展示了一个在一定程度上*拒绝*预测的调度器：它直接问每个任务要多长的时间片。第 22 章在内存上重演了先知问题，而 LRU 的预测在循环面前一败涂地。

::scene advice

预测之外的另一条路是去问，这就是本书关于*建议*的那段旁注：`nice`、[[madvise|`madvise`]]、知情预取。苹果的 [[thread-qos|QoS 类别]]、EEVDF 的时间片请求、[[fadvise|`posix_fadvise`]] 走的都是这条路。真实系统最终两样都做：程序知道的时候就问，不知道的时候就从历史里猜，再备好一次重置，留给猜错的时候。在大模型推理里，预测一个请求会生成多少 [[llm-token|token]] 成了新的“突发长度”问题，见[大模型推理里的护航效应](/notes/llm-convoy)。
