::scene overview

2023 年 6 月，加州大学伯克利分校的一个团队发布了 [[vllm|vLLM]]——在此前两个月里，[[vicuna|Vicuna 演示和 Chatbot Arena]] 背后跑的就是这个推理系统。他们的博客文章一开头就给出一个测量结果：已有系统因为碎片和过度预留，浪费了为每个请求的 [[kv-cache|KV 缓存]]所留内存的 60% 到 80%；用他们的设计，浪费不到 4%。背后的论文由 Woosuk Kwon、Zhuohan Li 等人完成，当年 10 月发表在 [[sosp|SOSP]] 上，题为 *Efficient Memory Management for Large Language Model Serving with PagedAttention*。

论文毫不掩饰这个想法的来历：把块看作页，把 [[llm-token|token]] 看作字节，把请求看作进程。这篇文章就顺着这个类比走下去：连续分配为什么会像第 15、16 章预言的那样失败，解决办法怎样对应到第 18 章，以及论文测了什么、没测什么。

::scene kvcache

## KV 缓存，以及它为什么这么大

[[transformer|Transformer]] 一次生成一个 token。为了生成第 *t* 个 token，每一层的[[attention|注意力]]都要拿当前 token 与同一请求之前所有 token 算出的*键*（key）和*值*（value）作比较。如果每一步都重算它们，几乎就是把此前的工作全部重做一遍，所以推理服务把它们存下来：这就是 **KV 缓存**。它属于某一个请求，与请求同生共死，每生成一步就长一个 token 的量。

论文以 [[opt-13b|OPT-13B]] 为例算了它的大小。每个 token 需要一个键向量和一个值向量（2），[[hidden-size|隐藏维度]] 5120，共 40 层，每个数 2 字节：

> 2 × 5120 × 40 × 2 字节 = 819200 字节 ≈ 每个 token 800 KB

一个长到模型上限 2048 个 token 的请求，大约需要 1.6 GB。在一块 40 GB 的 [[gpu|A100]] 上，论文给出的内存构成是：约 65% 给模型[[model-parameters|权重]]，接近 30% 给 KV 缓存。算下来，那大约是 12 GB，只够大约七个满长度的请求。论文自己的总结是：即便把所有可用内存都给 KV 缓存，也只能容纳几十个请求。

生成过程[[memory-bound|受限于内存]]：每一步都要把全部权重读一遍，只为每个请求产出一个 token，所以只有把许多请求批在一起，GPU 才算用得好，而批的大小取决于能放下多少份 KV 缓存。论文指出，算力增长快于内存：从 A100 到 H100，[[flops|FLOPS]] 翻了一倍多，显存最大仍是 80 GB。浪费掉的 KV 缓存，就是被挡在批次之外的请求。

::scene contiguous

## 连续分配：又是第 15、16 章

深度学习框架偏爱连续的[[tensor|张量]]，于是早先的推理系统把每个请求的 KV 缓存存成一整段连续区域。请求开始时并不知道最终会有多长，所以它们按*可能的最大*长度预留。

::chapter vm-paging

论文点出了三种浪费，每一种在书里都有名字：

- **预留的槽位。** 为请求以后要生成的 token 留的空间。它终究会被用上，但在等待期间，它占着本可以马上给别的请求用的内存。
- **内部碎片。** 为请求*永远*不会生成的 token 留的空间，因为请求远在达到上限之前就结束了。这正是第 15 章里基址/界限的浪费：一次分配按整个地址空间的大小来，中间留着一段没用上的空隙。
- **外部碎片。** 分配器发放变长内存块后，不同请求的区域之间留下的空隙。这是第 16 章分段遇到的问题，也是第 17 章的全部主题。

论文测量了问题有多严重：在它对已有系统的复现中，KV 缓存内存里只有 20.4% 到 38.2% 存着真正的 token 状态，其余都是预留和碎片。

::scene blocks

## 块与块表

PagedAttention 直接套用了第 18 章：

- KV 缓存被切成 **KV 块**，每块存放固定数量 token 的键和值，默认 16 个。
- 每个请求看到的是一串**逻辑块**，按 token 顺序编号为 0、1、2……，就像进程看到自己地址空间里的第 0、1、2……页。
- GPU 内存被切成**物理块**，好比页帧。任何物理块都能装任何逻辑块。
- 每个请求有一张**块表**，把逻辑块映射到物理块；每个表项还记录这个块已填了几个槽位。

物理块按需分配：请求的 token 填满上一个块时才分配下一个，所以不会为尚未生成的 token 预留任何东西。除最后一块外每块都是满的，于是每个请求的浪费不到一个块；而因为任何空闲块都合用，外部碎片也消失了。

下面是论文里的示例，为了简短，块大小取 4。一个请求带着 7 个 token 的提示词到来。

::scene grow

| 步骤 | 事件 | 逻辑块 0 | 逻辑块 1 | 逻辑块 2 |
|---|---|---|---|---|
| 提示词 | 存入 7 个 token | 物理块 7，已填 4 | 物理块 1，已填 3 | 无 |
| 解码第 1 步 | 写入第 8 个 token | 物理块 7，已填 4 | 物理块 1，已填 4 | 无 |
| 解码第 2 步 | 第 9 个 token 需要新块 | 物理块 7，已填 4 | 物理块 1，已填 4 | 物理块 3，已填 1 |

逻辑块 0 和 1 落在物理块 7 和 1 上，二者并不相邻，也不需要相邻。生成的第一个 token 填满了物理块 1 的最后一个空槽。第二个发现逻辑块 1 已满，于是块管理器分配一个空闲物理块（3），并在表里加一项。每一步都只是更新一下表，什么都不用复制。

::scene walk

代价转移到了注意力计算里。标准的注意力内核读取一整段连续的键值张量；PagedAttention 的内核则要遍历块表，一块一块地从各自所在之处取出键和值——每次注意力计算都是一次软件实现的页表遍历。论文测得这个内核的延迟比 [[fastertransformer|FasterTransformer]] 的连续内核高 20% 到 26%。作者认为端到端的影响不大，因为受影响的只有注意力这一个算子。

:::fold 从 token 位置到物理槽位
::scene split

这里的地址转换，就是第 18 章的地址拆分，只是把字节地址换成了 token 位置。设块大小为 *B*：

```py
# 伪代码：请求中的第 t 个 token 存在哪里？
def kv_slot(block_table, t, B=16):
    logical = t // B          # 相当于 VPN
    offset  = t % B           # 相当于页内偏移量
    physical = block_table[logical]
    return physical, offset   # 键/值位于 kv_pool[physical][offset]
```

*B* 是 2 的幂时，除法和取余就是一次移位和一次掩码，与把虚拟地址拆成页号和偏移量一模一样。

为一个新 token 计算注意力的内核，大致是这样：

```py
# 伪代码：在分页的 KV 缓存上做注意力，一个查询、一层
def paged_attention(q, block_table, n_tokens, kv_pool, B=16):
    scores, values = [], []
    for logical in range((n_tokens + B - 1) // B):
        k_blk, v_blk = kv_pool[block_table[logical]]     # 取出一个块
        filled = min(B, n_tokens - logical * B)
        scores += [q @ k_blk[i] for i in range(filled)]
        values += [v_blk[i] for i in range(filled)]
    w = softmax(scores)
    return sum(wi * vi for wi, vi in zip(w, values))
```

真实的内核让多个 GPU 线程并行处理各个块，并且边算边维护 [[softmax|softmax]] 的统计量，而不是把每个分数都存下来；但间接寻址是一样的：每个块查一次表，而不是每个 token 查一次。这就是块大小要紧的原因：块越大，查表越少、连续读取越长，最后一块的浪费也越多。
:::

::scene split

## 看地址怎样拆分

本章的分页实验展示的正是 PagedAttention 所用的地址转换。带着类比来读它：64 字节的地址空间就是一个请求的各个 token 位置，每个 16 字节的页就是一个有 16 个 token 槽位的 KV 块，页表就是这个请求的块表。

::lab Paging

可以试试这些：

- 把虚拟地址从 0 滑到 63，观察两部分。高两位选出逻辑块，低四位——块内的槽位——原样通过。
- 留意四个页落在哪里：页帧 3、7、5、2。相邻的逻辑块散落在物理内存各处，而计算对此毫不在意。正是这种散落，让 vLLM 可以把任何空闲块分给任何请求。
- 想象请求再长一个 token，越过地址 63。实验里的表是固定的，没有第 4 页；在 vLLM 里，块管理器会随便取一个空闲页帧，往表里追加一项。增长只需一个表项，从不需要复制。

这个实验是用字节地址的简化分页模型，不是 GPU 的模型，但算术是一样的。

::scene share

## 共享：写时复制与前缀

藏在一张表后面的定长块，作用不止于消除碎片。和操作系统里一样，它们让**共享**变得廉价。论文在三个地方用到了这一点。

**并行采样。** 为同一个提示词要几个不同的续写，这些样本就共享提示词。vLLM 只存一份提示词的 KV 块，让每个样本的块表都指向它们，并为每个物理块维护一个**[[reference-count|引用计数]]**。论文的例子里，两个样本共享物理块 7 和 1，引用计数都是 2。当某个样本要往共享块——也就是它最后那个未填满的块——里写入时，vLLM 采用**块粒度的[[copy-on-write|写时复制]]**：分配一个新块，复制数据，让这个样本的表指向副本，并把原块的计数减一。这就是缩小版的 [[fork-exec|`fork()`]]，也是 Redis 做快照所依赖的同一种机制（见 [fork() 那篇](/notes/fork-redis)）。

**束搜索。** 束搜索（beam search）同时保留若干候选续写，不断淘汰一些、扩展另一些。候选之间不仅共享提示词，还共享大段已生成的文本，而且随着候选分叉和消亡，共享关系不断变化。有了块表，分叉一个候选就是复制一张小表、给引用计数加一；淘汰一个候选就把计数减一，计数归零的块回到空闲列表。

::scene prefix

**共享前缀。** 许多请求都以同样的[[system-prompt|系统提示词]]或示例开头。论文允许服务提供方为预定义的前缀预留物理块，并把它们映射进新请求的块表，这样前缀只需计算一次。vLLM 后来的版本把它推广成了*自动前缀缓存*（automatic prefix caching）：每个满块由它自身 token 与前一块哈希值共同算出的[[hash|哈希]]来标识，于是一个哈希值就代表了一整段前缀，新请求可以复用每一个匹配上的块。暂时无人使用的缓存块按[[lru|最近最少使用]]的顺序待在空闲队列里，直到需要内存时才被逐出——这就是给提示词用的[[page-cache|页缓存]]。[[sglang|SGLang]] 的 RadixAttention 则把同样的复用组织成一棵前缀树（见 [基数树那篇](/notes/radix-trees)）。

:::fold 写时复制，一块一块来
::scene share

沿用论文的并行采样例子，块大小为 4：7 个 token 的提示词，两个样本 A 和 B。

1. **提示词阶段。** 提示词填满逻辑块 0 和 1，存放在物理块 7 和 1 中。两个样本的块表都指向 7 和 1，每块引用计数为 2。提示词的键和值只有一份。
2. **A 生成第一个 token。** 它应当写进逻辑块 1 的最后一个槽位，但物理块 1 是共享的（计数为 2）。vLLM 分配一个新物理块，比如 3，把块 1 已填的三个槽位复制过去，把 A 的 token 写进第四个槽位，让 A 的逻辑块 1 指向 3，并把块 1 的计数减到 1。
3. **B 生成第一个 token。** 块 1 现在计数为 1，归 B 独有，直接原地写入，无需复制。
4. **两者继续生成。** 此后任一样本新分配的块从一开始就是私有的。块 7，即提示词的前四个 token，在两个样本的整个生命期内都保持共享。

自始至终只复制了一个块，而且只是提示词中没填满整块的那部分。提示词越长，共享的比例就越大。下文论文测得的节省量，在很大程度上取决于负载中提示词和输出的长度。
:::

## 内存用尽时：换出与重算

按需分配意味着内存可能在某个请求生成到一半时用完，于是 vLLM 必须抢占。它的选择就是第 21 章的那些。

它按先来先服务调度请求，所以块不够时，最晚到达的请求最先被抢占。逐出是**全有或全无**的：一个序列的块要么一起逐出，要么都不动，因为缺了任何一部分 KV 缓存，请求就走不了下一步。共享块的序列，比如同一次束搜索的各个候选，作为一个*序列组*（sequence group）一起调度、一起被抢占。

被逐出请求的块有两条去路：

- **换出（swapping）。** 把块复制到 CPU 内存——这个请求的[[swap|交换空间]]——等它重新被调度时再复制回来。
- **重算（recomputation）。** 把块直接丢掉，之后把提示词和已生成的 token 一起送进模型跑一遍，重新得到它们。

重算之所以可行，是因为 KV 缓存是派生数据：就像文件的[[clean-page|干净页]]，随时可以从源头重建。论文发现，块小时换出代价很高，因为要做许多次 CPU 与 GPU 之间的小传输；重算的代价则与块大小无关。块大小在 16 到 64 之间时，两者的端到端表现相当。

::scene measured

## 论文实际测了什么

头条结论——在相同延迟下，吞吐量是 FasterTransformer 和 [[orca|Orca]] 的 2 到 4 倍——是成立的，但也需要仔细读。

实验用的是 OPT-13B、66B 和 175B，共享前缀实验另用 [[llama|LLaMA-13B]]，跑在 Google Cloud 的 A100 上：13B 用一块 40 GB 的 GPU，66B 用四块，175B 用八块 80 GB 的 GPU。负载是由 [[sharegpt-alpaca|ShareGPT 和 Alpaca]] 数据集构造的请求轨迹，到达时间服从不同速率的[[poisson|泊松分布]]，每次跑一小时（175B 为控制成本只跑 15 分钟）。指标是*归一化延迟*：每个请求的端到端延迟除以其输出长度，再取平均。吞吐量大致就是系统在这个延迟飙升之前能承受的请求速率。

基线需要说明一下。Orca 没有公开可用的版本，作者自己实现了一份，分三个变体，区别只在于每个请求预留多少：*Orca (Max)* 一律预留到 2048 个 token 的上限；*Orca (Pow2)* 最多超额预留 2 倍；*Orca (Oracle)* 事先被告知每个请求真实的输出长度——这是任何真实系统都不可能知道的。FasterTransformer 自身没有调度器，作者为它写了一个。

:::fold 那些数字，以及每个数字在比什么
- **请求速率，ShareGPT。** 在相近延迟下，是 Orca (Oracle) 的 1.7 到 2.7 倍，Orca (Max) 的 2.7 到 8 倍；最高可达 FasterTransformer 的 22 倍。
- **批大小。** 在 OPT-13B、ShareGPT 上，vLLM 同时处理的请求数是 Orca (Oracle) 的 2.2 倍、Orca (Max) 的 4.3 倍。
- **存放 token 状态的内存占比。** 各 Orca 变体为 20.4% 到 38.2%。博客给出的 vLLM 浪费不到 4%。
- **共享节省的内存。** 并行采样：Alpaca 上 6.1% 到 9.8%，ShareGPT 上 16.2% 到 30.5%。束搜索：Alpaca 上 37.6% 到 55.2%，ShareGPT 上 44.3% 到 66.3%。
- **按解码方式相对 Orca (Oracle) 的提升**，OPT-13B、Alpaca：从基本采样的 1.3 倍，到束宽为 6 的束搜索的 2.3 倍。
- **共享前缀**，LLaMA-13B 翻译任务：单样例前缀时吞吐量是 Orca (Oracle) 的 1.67 倍，五样例前缀时为 3.58 倍。
- **代价。** 单看注意力内核，比 FasterTransformer 的慢 20% 到 26%。

两点提醒。对内存管理器而言，与 Orca (Oracle) 的比较才是公平的那个：Oracle 为每个请求恰好预留所需，剩下的差距就只来自碎片和共享。更大的倍数来自预留到上限的基线。另外，博客里“吞吐量最高 24 倍”比的是 Hugging Face Transformers——一个通用的模型库，而不是推理服务系统——这和论文的结论是两回事。
:::

## 理想设计在哪里弯折

这个设计带着分页的种种权衡，每一项在书里都有对应。

- **块大小。** 块太小，用不满 GPU 的并行度；块太大，每个请求最后一块浪费更多，可共享的部分也更少。ShareGPT 上 16 到 128 个 token 最好，Alpaca 的序列较短，16 和 32 最好，默认值定为 16——这是第 18 章的页大小权衡在新负载上的又一次测量，[变长与定长那篇](/notes/fixed-vs-variable) 会在别的系统里继续追踪它。
- **软件里的地址转换。** 查块表的逻辑长在每一个注意力内核里，所以每个新内核都得专门为分页内存来写。vAttention（Prabhu 等，ASPLOS 2025）主张改用 CPU 的办法：借助 GPU 的虚拟内存支持，给每个请求一段连续的虚拟地址范围，再按需把物理内存映射进去。它报告的吞吐量比 [[flashattention|FlashAttention 和 FlashInfer]] 中基于 PagedAttention 的内核最高高出 1.23 倍。虚拟空间里连续、底下分页，这正是第 18 章给进程的东西。
- **调度。** 内存管理决定能放下多少请求；运行哪些、何时运行，则是调度问题。vLLM 建立在迭代级调度之上，每一步都重新组批，这是 [护航效应那篇](/notes/llm-convoy) 的主题。释放的块与接纳的请求，是同一个决策的两面。

::scene overview

## 回到书里的那条线

把第 18 章和这篇论文并排放好，几乎每个术语都能找到搭档：

1. **页** ↔ KV 块，**页帧** ↔ 物理块，**页表** ↔ 块表。
2. **按需分配** ↔ 只在上一块满了时才分配新块。
3. **`fork()` 之后的写时复制** ↔ 在样本和候选之间共享、带引用计数的块。
4. **交换空间与页面替换** ↔ 把块换出到 CPU 内存，或干脆重算。
5. **页缓存** ↔ 对共享提示词块的前缀缓存。

本书把分页追溯到 1960 年代初的 Atlas 计算机。它在那里解决的问题，正是 PagedAttention 在 GPU 上解决的问题：许多相互独立、不断增长、最终大小未知的区域，争抢同一块物理内存。只要问题长成这个样子，第 18 章的答案就会再次奏效。
