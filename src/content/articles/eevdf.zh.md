::scene overview

2023 年 10 月发布的 Linux 6.6，悄悄换掉了调度器的心脏。自 2007 年的 2.6.23 起，几乎每一台 Linux 机器上“下一个该谁运行”都由完全公平调度器（CFS）决定；从 6.6 开始，这份工作交给了一个叫 **EEVDF** 的算法——*最早合格虚拟截止期优先*（Earliest Eligible Virtual Deadline First）。这个算法并不新：它出自 Ion Stoica 和 Hussein Abdel-Wahab 1995 年的一份技术报告，也就是本书第 9 章末尾引用的 [SA95]。

没人会为了好玩去换调度器。CFS 是公平的，也足够快，从手机到超级计算机都跑得动。它做不干净的，是每个调度器都要回答的第二个问题。这篇文章讲的就是这第二个问题，以及一个三十年前的想法如何只给每个任务多记一个数，就把它答好了。

::scene two-questions

## 两个问题，一个旋钮

分时 CPU 的调度器要回答两个不同的问题：

- **分多少？** 在足够长的时间里，每个任务应该得到 CPU 的几分之几？这是第 9 章的比例份额问题：彩票、步长、权重。
- **多快轮到？** 一个任务变成可运行之后，最多要等多久才能运行？这是第 7 章的响应时间问题。

步长调度和 CFS 把第一个问题答得很漂亮，第二个问题却只是碰巧答上。两者都给每个任务记一个虚拟时间计数器（步长调度叫 *pass*，CFS 叫 *vruntime*），权重越大的任务计数器走得越慢，然后总是运行计数器最小的那个。久而久之，每个任务的计数器以同样的步调前进，于是每个任务按权重比例分到 CPU。但这条规则里没有任何一句话规定：在接下来几毫秒里，一个任务*什么时候*轮到。

CFS 用一堆启发式规则填补这个空白：目标延迟、最小粒度、决定被唤醒任务能否抢占当前任务的唤醒粒度，以及给睡眠者的补偿，免得交互式程序因为睡过觉而吃亏。这些规则多年来够用了。但用户手里只有一个旋钮——*nice* 值——它把份额和延迟绑在一起拧。想让音频[[thread|线程]]响应更快，就调低它的 nice 值，结果你同时也多分给了它一份它根本用不上的 CPU。

多年来一直有开发者提议在 CFS 之上再加第二个旋钮，叫“latency nice”。Peter Zijlstra 在 2023 年 3 月给出的回答是：换掉底下的算法，让第二个旋钮从数学里自然长出来，而不是硬拧上去。这个算法就是 EEVDF。

::scene vruntime

## 再看虚拟时间

::chapter cpu-sched-lottery

从第 9 章已经讲过的内容出发。每个任务 *i* 有一个权重 *w*~i~（由 nice 值换算而来，nice 0 对应权重 1024）和一个虚拟运行时间 *v*~i~。任务实际运行 Δ*t* 时，它的虚拟运行时间增加 Δ*t* · 1024 / *w*~i~：重的任务老得慢，轻的任务老得快。CFS 运行 *v*~i~ 最小的任务，步长调度运行 pass 最小的任务——这是同一条规则的两个名字。

EEVDF 多引入一个量：[[run-queue|队列]]的**虚拟时间** *V*，即所有可运行任务虚拟运行时间的加权平均。

> V = Σ w~i~ · v~i~ / Σ w~i~

可以把 *V* 理解为“一台绝对公平的处理器此刻会把每个任务推进到哪里”。在理想的、可以无限细分的 CPU 上，所有任务齐步前进，每个 *v*~i~ 时时刻刻都等于 *V*。真实的 CPU 一次只能跑一个任务，于是有的任务跑到了 *V* 前面，有的落在后面。

::scene lag

## 滞后量：你被欠了多少

与理想状态之间的差距叫**滞后量**（lag）：

> lag~i~ = w~i~ · (V − v~i~)

滞后量为正的任务*落后*了：它得到的 CPU 少于应得份额，别人欠它时间。滞后量为负的任务*超前*了：它多拿了。EEVDF 把滞后量大于等于零的任务称为**合格**（eligible），也就是 *v*~i~ ≤ *V* 的任务。

这是规则的前一半，负责“分多少”：只有没有超出应得份额的任务才可以运行。超前的任务必须等别人追上来、等 *V* 越过它。无论规则的后一半在合格任务里怎么挑，没有任何任务能长期多拿。

:::fold 为什么所有滞后量加起来恰好为零
把定义展开，对所有可运行任务求和：

Σ lag~i~ = Σ w~i~ · V − Σ w~i~ · v~i~ = V · Σ w~i~ − Σ w~i~ · v~i~。

而按 *V* 的定义，Σ *w*~i~ · *v*~i~ = *V* · Σ *w*~i~，所以总和恰好为零。

滞后量是零和的：一个任务超前的每一毫秒（按权重计），都对应着别人落后的一毫秒。这在实践中有两个后果：

- 至少总有一个任务是合格的——不可能所有人都超前。调度器永远不会陷入“谁都不能跑”的境地。
- 当一个任务带着它的滞后量离开队列（睡眠或退出）时，*V* 必须移动，账才能平。这就是为什么内核对任务离开和回来时携带什么滞后量格外小心，下文会讲到。

真实的内核并不会每次决策都从头计算 *V*。Linux 维护的是相对某个参考点的累加和 Σ *w*~i~ · (*v*~i~ − *v*~0~) 以及总权重，任务加入、离开或运行计费时增量更新，求平均只需一次除法。
:::

::scene deadline

## 截止期：什么时候该轮到你

规则的后一半负责“多快轮到”。任务每次要 CPU，都要的是一个具体的量：一个 *r*~i~ 毫秒的**请求**，内核称之为任务的*时间片*（slice）。EEVDF 把这个请求换算成一个**虚拟截止期**（virtual deadline）：

> d~i~ = v~i~ + r~i~ · 1024 / w~i~

它表示：如果处理器绝对公平，任务应当在虚拟时间走到哪里之前拿到它要的 CPU。完整的规则读起来就是算法的名字：**在合格的任务中，运行虚拟截止期最早的那个。**

看看请求大小起了什么作用。一个请求 3 ms 时间片的任务，截止期在虚拟未来 3 ms（按权重缩放）处；一个请求 0.5 ms 的任务，截止期只在 0.5 ms 之外，于是在截止期排序里排得更前，更早运行。但它只能跑 0.5 ms，请求就完成了，随后获得一个新的截止期。请求短时间片，换来的是更早、但更零碎的服务；换不来更多的服务——因为合格性依然把每个任务封顶在它的份额上。

这正是 CFS 缺少的那种分离：**权重**决定分多少，**时间片**决定多快轮到。

下面是三个等权重任务的一个快照（虚拟时间以毫秒计，为便于阅读省去权重缩放）：

| 任务 | v | 时间片 r | 截止期 d = v + r | 滞后量 (V − v) | 合格？ |
|---|---|---|---|---|---|
| A | 10 | 3 | 13 | +2 | 是 |
| B | 12 | 0.75 | 12.75 | 0 | 是 |
| C | 14 | 0.5 | 14.5 | −2 | 否 |

*V* 是平均值 12。CFS 会运行 vruntime 最小的 A。EEVDF 运行的是 **B**：A 和 B 都合格，而 B 的截止期更早。C 请求的时间片最短，但它已经超出了应得份额，短时间片此刻帮不了它。A 从长远看什么也没损失：它依然合格，依然被欠着 2 ms，B 的短请求一完成就轮到它。

:::fold 内核代码长什么样
::scene tree

这个决策在 `kernel/sched/fair.c` 的 `pick_eevdf()` 里。最直白的做法是扫描所有任务，那是 O(n)；所以可运行任务放在一棵红黑树里，每个节点还缓存额外信息：

- Linux 6.6 里，树沿用 CFS 的老办法按 vruntime 排序，每个节点额外缓存其子树中最早的截止期。
- 从 Linux 6.8 起，树改为按**截止期**排序，每个节点缓存其子树中**最小的 vruntime**。从最左边（截止期最早）一侧往下找时，只要某棵子树的最小 vruntime 已经超过 *V*，里面就没有合格任务，可以整棵跳过。

两种设计下，挑选都只是沿平衡树走一趟，O(log n)。常见情况更便宜：最左节点是缓存好的，只要它合格，答案就是它。

下面是 6.8 之后搜索过程的简化伪代码（真实函数还要处理不在树里的当前运行任务，以及若干特性开关）：

```c
/* pseudo-code, simplified from kernel/sched/fair.c (6.8+) */
entity *pick_eevdf(tree *t, u64 V)
{
    node *n = t->root;
    if (eligible(t->leftmost, V))           /* fast path */
        return t->leftmost;
    while (n) {
        if (n->left && n->left->min_vruntime <= V) {
            n = n->left;                     /* an eligible, earlier deadline exists to the left */
            continue;
        }
        if (eligible(n, V))
            return n;                        /* nothing eligible to the left: this is it */
        n = n->right;
    }
    return NULL;
}
```

比细节更值得记住的是模式：这是一棵增强树（augmented tree）——在每个节点里缓存子树的摘要，让查询能整棵剪掉子树。同样的技巧出现在区间树、内核管理[[vma|虚拟内存区域]]的结构，以及数据库索引里。
:::

## 看它跑起来

下面的实验运行一个简化版 EEVDF，有三个任务。A 和 B 是 CPU 密集型，请求默认的 3 ms 时间片。C 是交互式的：运行 0.5 ms，睡 3.75 ms，再醒来——就像一个处理输入事件的线程。下方面板就是本文的那条数轴：阴影区是“合格”，竖线是 *V*，圆点是任务的 vruntime，横条一直延伸到它的截止期。

::lab Eevdf

可以试试这些：

- 让 C 保持 3 ms，单步走过一次唤醒。C 醒来时是合格的，但它的截止期并不比正在运行的任务早，只能等对方的请求结束。它的平均等待在 2.5 ms 左右。
- 把 C 切到 0.5 ms。现在刚醒来的 C 截止期最早，几乎立刻就能运行，平均等待降到 1 ms 左右。剩下的那部分，是 C 跑完一轮后超前于份额、等 *V* 追上来的时间。
- 同时留意 CPU 份额。A 和 B 依然几乎平分 C 用剩的时间。C 的份额略有上升，只是因为它等得少了、醒得更勤了——它*应得*的份额并没有变。
- 把 A 的权重调成两倍。A 在数轴上的横条变短（截止期在虚拟时间上更近了），A 的份额升向 CPU 密集时间的三分之二。这一切都与时间片无关。

这个实验是简化过的：固定 0.25 ms 的时间步长，单个 CPU，被唤醒的任务只要会被选中就立即抢占。最后这一点大致对应 Linux 从 6.12 起对短时间片任务的做法，后面几节会讲到。

::scene sleep

## 睡眠：带着你的滞后量

任何公平调度器最难处理的，都是离开又回来的任务。

CFS 用一条启发式规则处理睡眠者：被唤醒任务的 vruntime 至少被提到队列最小 vruntime 减去半个目标延迟的位置。这份补偿让交互式任务很灵敏，但它是一笔固定的补贴，与任务睡下时实际被欠了多少毫无关系。

EEVDF 的答案直接来自滞后量：任务带着它当时的滞后量离开；回来时，被放到一个让滞后量保持不变的位置，即 vruntime 设为 *V* − lag / *w*。离开时被欠着时间的任务，回来时依然被欠着，很快就能运行；离开时*超前*的任务（滞后量为负），回来时依然超前，必须等 *V* 追上来。睡一觉再也洗不掉透支。这和 [第 8 章](/virtualization/cpu-sched-mlfq) 里 MLFQ 记账防“钻空子”的直觉一脉相承，只是变得精确了。

::scene delayed

但永远保留滞后量也不对：一个睡了一小时的任务，不该带着一小时前的一毫秒欠账或债权回来。Linux 6.6 用保存的滞后量放置被唤醒的任务，并做了缩放，免得任务自己的加入挪动了 *V*、把这份滞后量吃掉。Linux 6.12 用**延迟出队**（delayed dequeue）补全了设计：一个在不合格状态下睡去的任务不会立刻离开队列，而是被标记为“延迟出队”留在原地，等它的负滞后量衰减完，才真正离开。欠账在虚拟时间里慢慢还清，而不是被随身带走或一笔勾销。

:::fold 为什么需要延迟出队
在睡下那一刻把滞后量存起来的问题在于：任务睡着时 *V* 仍在前进，而且前进的方式取决于其他还有谁在运行。某一刻记下的负滞后量，过一阵再用，惩罚可能重得多，也可能轻得多。

让不合格的睡眠者留在队列上，就能让常规机制来处理它：它的 vruntime 不动，*V* 从它身边走过；等它的滞后量回到零，才真正出队，两不相欠。代价是复杂性：一个“正在睡眠”的任务如今还逗留在运行队列里，所有统计可运行任务数、计算负载的代码都得学会分辨。一些针对 6.12 的[[regression|回归]]报告，就是靠关掉它来定位问题的。这一行为由调度器特性开关 `DELAY_DEQUEUE` 控制，排查问题时可以在 [[debugfs|`/sys/kernel/debug/sched/features`]] 里把它关掉。
:::

## 新的旋钮：请求一个时间片

头一年，第二个旋钮只存在于内核内部：所有普通任务都用同一个基础时间片。在 6.6 里它是 0.75 ms 乘以 1 + log~2~(CPU 数)（CPU 数最多按 8 计），所以多数机器上是 3 ms。2025 年的一个改动把基数减到 0.7 ms，对应 2.8 ms。

Linux 6.12 把这个旋钮交给了用户空间：一个普通的公平任务可以通过 `sched_setattr()` [[syscall|系统调用]]的 `sched_runtime` 字段请求时间片。这个字段原本就为 [[sched-deadline|`SCHED_DEADLINE`]] 任务存在，在那里含义要严格得多。内核会把取值限制在合理范围内。也是从这个版本起，被唤醒任务的时间片若比当前任务短，就可以抢占它，于是短时间片能直接转化为更短的唤醒延迟。

```c
#include <linux/sched/types.h>   /* struct sched_attr */
#include <sys/syscall.h>
#include <unistd.h>

/* 为调用线程请求 1 ms 的时间片；它仍是一个普通的公平任务 */
int request_short_slices(void)
{
    struct sched_attr attr = {
        .size          = sizeof(attr),
        .sched_policy  = 0,             /* SCHED_OTHER */
        .sched_nice    = 0,             /* sched_setattr 也会设置 nice：显式写出来 */
        .sched_runtime = 1000 * 1000,   /* 单位：纳秒 */
    };
    return syscall(SYS_sched_setattr, 0, &attr, 0);   /* pid 0 = 当前线程 */
}
```

权重依旧来自 nice 值，时间片则来自这里。音频回调线程可以要短时间片而不多要 CPU；批处理任务可以要长时间片，让[[cpu-cache|缓存]]保持温热。这正是 latency nice 想达到的分离——却不必发明一种新的优先级。

:::aside EEVDF 不是什么
EEVDF 里的“截止期”是一个虚拟的排序键，不是承诺。EEVDF 不是实时调度器，也和 Linux 的 `SCHED_DEADLINE` 策略无关——后者借助[[admission-control|准入控制]]和[[edf|最早截止期优先（EDF）]]算法，确实提供保证。负载很重时，EEVDF 下的任务照样要排在别人的公平份额后面。它保证的是比例份额，以及任何任务的滞后量偏离都有界。
:::

## 理想规则在哪里弯折

干净的规则碰上真实的硬件和负载，在几个地方长出了旋钮或启发式：

- **跑到持平（run to parity）。** 严格的 EEVDF 每个[[tick|时钟节拍]]都要重新决策。Linux 让当前任务一直运行，直到用完它的时间片或追上 *V*（零滞后点），避免在几乎相等的任务之间来回切换。这就是 `RUN_TO_PARITY` 特性。
- **唤醒抢占。** 被唤醒的任务如果会被选中，就会抢占，但“跑到持平”通常会保护当前任务。从 6.12 起，时间片更短的被唤醒任务可以突破这层保护（`PREEMPT_SHORT`）。
- **分组。** 有了 [[cgroup|cgroup]]，EEVDF 在层级的每一层都运行：一个[[container|容器]]在父队列里是一个实体、一个权重，内部再有自己的任务队列——参见 [Kubernetes 那篇](/notes/k8s-shares)。
- **多 CPU。** 以上一切都发生在每个 CPU 自己的运行队列里。任务在队列之间的迁移仍是[[load-balancing|负载均衡器]]的事，[第 10 章](/virtualization/cpu-sched-multi) 的多处理器权衡一个也没变。

这次切换还有干净的数学掩盖掉的代价。一些负载在 6.6 之后、又在 6.12 之后出现了性能[[regression|回退]]。应对的办法是围绕唤醒和放置的修补与调优——那正是调度器里启发式扎堆的地方——而不是改动核心规则。

::scene lineage

## 回到书里的那条线

把第 9 章和这篇文章摆在一起，谱系很短：

1. **彩票调度**用概率实现份额。
2. **步长调度**为每个任务记一个 pass 值，以确定的方式实现同样的份额。
3. **CFS** 是带权重、用红黑树实现的步长调度，只是把 pass 叫作 vruntime。
4. **EEVDF** 保留了这一切，把公平份额显式化为 *V* 和滞后量，再加上第二个键——虚拟截止期——来决定先后，而不碰份额。

只要一种资源被形状各异的“流”共享，“分多少”和“多快轮到”的分离就会出现。在网络里，[[fair-queueing|公平排队]]调度器给每条流一个虚拟完成时间；一个叫 WF²Q 的改进（Bennett 与 Zhang，1996）加入的正是 EEVDF 的合格规则：只有虚拟开始时间已到的分组才能发送，否则一条流可以突发着跑到份额前面。近来，大模型推理系统用“虚拟 [[llm-token|token]] 计数器”在请求大小悬殊的用户之间公平地分享 GPU——同一套记账，只是单位从毫秒换成了 token。

本书这一章的结尾提到 Linux 已经转向了 EEVDF。现在你知道为什么了：份额从来不是问题；问题在于一个数字不得不同时代表两件事。
