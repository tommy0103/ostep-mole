::scene overview

开几个标签页，再打开浏览器自带的任务管理器（Chrome 里在“更多工具”下面）。你看到的不是一个程序，而是一张列表：一个浏览器进程、一个 GPU 进程、网络服务之类的若干实用进程、每个站点一个渲染进程，外加几个属于扩展的进程。每一行都有[[pid|进程 ID]]、内存占用和 CPU 列。这就是第 4 章讲的进程列表，只不过管理它的不是内核，而是一个应用程序。

浏览器并不是一开始就这样。2008 年 9 月 Chrome 首次发布时，多进程架构正是它的头号卖点。Chromium 团队的设计文档回顾了它要解决的问题：在当年的浏览器里，网页或插件里的一个 bug 就能让整个浏览器连同所有打开的标签页一起崩掉。十年后，设计又变了一次。2018 年 1 月公开的 [[spectre|Spectre 和 Meltdown]] 攻击表明，进程内运行的代码可以读到它本不该看到的内存。Chrome 67 的回应是为桌面用户默认开启**站点隔离**（Site Isolation）：每个站点都有专属于自己的渲染进程。为此，Chrome 团队接受了 9%～13% 的总内存增长（2018 年 10 月实测）。

对一个内存占用早已成为段子的产品来说，这是一个昂贵的决定。这篇文章要讲清楚为什么它是对的，以及为什么答案是*进程*，而不是[[thread|线程]]或更聪明的语言运行时。

## 用书里的话来问

::chapter cpu-intro

::scene isolation

第 4 章把进程定义为运行中的程序，并列出了它的组成：它能访问的内存（它的**地址空间**）、寄存器，以及打开的文件等 I/O 状态。操作系统为每个程序维护一份这样的东西，而本书接下来的二十章，都在讲操作系统如何让每个进程相信自己独占了整台机器。

浏览器恰恰需要这种“相信”，只是理由不同。操作系统虚拟化 CPU 和内存，是为了让许多程序*方便地*共享一台机器；浏览器则需要*安全地*运行许多段不可信的代码：新闻网站、网上银行、广告脚本、一个你不小心点开的页面。每一段都是陌生人写的程序，其中一些怀有敌意，而它们全都跑在一个几百万行 C++ 写成的引擎上——这样的引擎必然有 bug。

所以浏览器的问题，就是带着戒心重问一遍第 4 章的问题：*最小的、出了故障或被人策反也不会殃及其他部分的执行单元是什么？* 线程当不了这个单元。同一进程里的线程按设计就共享一个地址空间，一个线程的 bug 可以把所有线程的数据写坏，一次成功的漏洞利用可以读到所有线程的数据。进程才是操作系统真正会去守护的最小单位：它的地址空间由硬件强制执行（第 13～15 章会讲），而离开它的唯一途径是一次由内核检查的[[syscall|系统调用]]（第 6 章会讲）。

## 分工：谁在哪里运行

::scene privilege

一个现代的、基于 Chromium 的浏览器，大致这样分配工作。细节随版本而变，格局则没有变。

| 进程 | 在里面运行什么 | 权限 | 它崩溃时 |
|---|---|---|---|
| 浏览器进程 | 窗口和标签页界面、用户配置、导航决策、管理其他一切的策略 | 你的用户账户拥有的全部权限 | 整个浏览器退出 |
| 渲染进程（每个站点一个或多个） | Blink 排版引擎、V8 JavaScript 引擎、页面自己的代码 | 处于沙箱中：几乎什么都不能做 | 该标签页或框架显示“崩溃”页面（sad tab） |
| GPU 进程 | 代表所有渲染进程与[[driver|显卡驱动]]打交道 | 比渲染进程高得多 | 浏览器本身不受影响 |
| 网络服务 | HTTP、缓存、Cookie | 受限的实用进程（多数平台上独立于浏览器进程） | 在新的实用进程中重启 |
| 其他实用进程 | 音频、存储、媒体解码 | 各不相同，多数在沙箱中 | 视具体服务而定 |

这张表遵循 Chromium 安全团队所说的**二选规则**（Rule of 2）：任何一段代码，在下面三个危险属性中最多只能占两个——处理*不可信的输入*（格式复杂、来源无法验证的任何数据），用*不安全的语言*写成（例如 C 或 C++），以*高权限*运行。渲染进程用 C++ 解析来自开放网络的 HTML、CSS、JavaScript 和图片，已经占了前两个，所以绝不能再有第三个。浏览器进程拥有第三个，所以它绝不能去解析网页内容；当它需要理解渲染进程发来的东西时，收到的是一条结构简单的消息，并且要逐项检查。

这正是要把工作放进进程的原因。浏览器进程是这个小系统的内核：它拥有资源，也掌握策略。渲染进程是它的用户程序：CPU 给得足够，有自己私有的地址空间，但不能直接碰任何要紧的东西。

## 一道崩溃边界

::scene crash

2008 年的设计主要是为了应对崩溃。每个渲染进程都是一个独立的操作系统进程，浏览器进程持有它的[[handle|句柄]]。当渲染进程因为空指针、栈溢出或者[[oom-kill|内存不足被杀]]而死掉时，操作系统会回收它的地址空间、关闭它的句柄——和第 4 章描述的任何进程一样。浏览器察觉到句柄发出的信号，在受影响的标签页里显示一张哭脸页面，并在下一次刷新或导航时启动一个新的渲染进程。其他标签页照常运行，因为它们依赖的东西没有一样放在那个死掉的进程的内存里。

同样的逻辑也决定了表里的其他几行。显卡驱动出了名地脆弱，Chromium 的设计文档把防范驱动问题列为 GPU 进程的首要目标。渲染进程从不直接调用驱动：它们把绘图命令写进[[shared-memory|共享内存]]，GPU 进程逐条读出命令，检查命令及其参数，然后才去调用真正的图形 API。如果驱动崩了，倒下的是 GPU 进程，而不是浏览器。网络服务也一样：当它运行在独立进程中时，崩溃后会在一个新的实用进程里重启；而在把它留在浏览器进程内部的配置下，文档说得很直白——整个浏览器会跟着一起崩溃。

这是把第 4 章的进程生命周期当作可靠性工具来用：创建进程足够便宜，可以按需进行；销毁进程——无论是主动还是被迫——都会清理掉它占有的一切。一个可能出故障的组件，放进一个操作系统知道如何拆掉的盒子里，才最安全。

:::fold 渲染进程的沙箱长什么样
::scene sandbox

把渲染进程放进独立进程只是第一步，第二步是拿走普通进程本来可以做的事。Chromium 把浏览器进程称为*代理*（broker），把被沙箱化的进程称为*目标*（target）：代理负责创建每个目标、给它一份策略，并代它执行策略允许的少数特权操作。沙箱的设计文档这样概括结果：渲染进程用到的几乎所有资源，都是浏览器先申请好，再把句柄复制给渲染进程的。

在 **Windows** 上，渲染进程使用一个[[access-token|受限令牌]]（restricted token）运行，几乎不带任何组和特权，[[integrity-level|完整性级别]]是最低的“不受信任”（Untrusted）。它被放在一个[[job-object|作业对象]]（job object）里，只能有一个进程，碰不到剪贴板和系统级设置；它还待在一个看不见的独立桌面上，无法给你的窗口发消息。

在 **Linux** 上有两层。[[namespace|命名空间]]这一层把渲染进程放进新的 PID 命名空间和网络命名空间，使它看不到其他进程、也连不上网络，并把它的文件系统根目录换成一个空的只读目录。随后，一个 **[[seccomp|seccomp-bpf]]** 过滤器会对渲染进程发出的每一次系统调用运行一小段 [[bpf|BPF 程序]]，拒绝名单之外的一切。既然离开进程的唯一途径就是[[trap|陷入内核]]（第 6 章），过滤这些陷阱就是能开出的最窄的门。

::scene zygote

Linux 上还有一个进程技巧。渲染进程不是用 [[fork-exec|`exec()`]] 启动的：浏览器启动时先拉起一个 **[[zygote|zygote]]** 进程，它把公共库加载并初始化一次，然后就等着。每个新的渲染进程都是 zygote 的一次 `fork()`，以[[copy-on-write|写时复制]]（copy-on-write）的方式共享 zygote 已初始化好的页面，Chromium 文档（2017 年）估计每个进程能因此省下最多约 8 MB。这和 [Redis 拍快照](/notes/fork-redis) 用的是同一个 fork 技巧，只是这里用来让进程更便宜。

::scene ipc

沙箱之所以有效，是因为浏览器不信任自己的渲染进程。每个 [[ipc|IPC]] 请求（“给我这个[[origin|源]]的 Cookie”）都要对照该进程被允许接触的范围来检查。一个渲染进程如果请求了它绝不该请求的东西，就会被当作已被攻破，直接终止。
:::

## 为什么 2008 年的设计不够

::scene shared

第一代多进程 Chrome 大致是每个*标签页*一个渲染进程。这挡住了崩溃的蔓延，沙箱也让被劫持的渲染进程没法在你的电脑上装恶意软件。但在一个标签页内部，来自多个站点的页面仍然共用一个渲染进程：一个嵌着别家广告 [[iframe|iframe]] 的新闻页面，两者跑在同一个进程里；脚本用 `window.open` 打开的同站页面会加入打开者的进程；一旦浏览器达到进程数上限，互不相干的标签页也开始共用进程。

::scene spectre

对崩溃来说，这没什么问题；对机密来说，问题很大。介绍站点隔离的论文直接列出了这种威胁：被攻破的渲染进程可以读取自己地址空间里的任何东西，其中就包括其他站点的文档。随后 Spectre 让攻击者连“攻破”这一步都省了：瞬态执行攻击让普通的 JavaScript 就能读到本进程中语言本不允许它触及的内存。在同一个地址空间里，浏览器用软件筑起的每一道墙，一夜之间都成了“建议”。

:::fold 为什么 Spectre 让地址空间成了唯一可靠的墙
JavaScript 引擎用软件执行许多规则：数组越界检查、类型检查、“一个站点的脚本不能读另一个站点的文档”。Spectre 类攻击利用的是处理器的一个习惯：在还不确定分支会不会走向某处之前，就*推测性地*执行那里的指令。一个注定失败的越界检查，仍然可能让几条指令带着越界读到的值跑起来。这些指令的结果会被撤销，但它们对[[cpu-cache|缓存]]造成的影响不会。攻击者通过测量后续内存访问的时间，就能一点一点地把那个值恢复出来。

关键在于*进程内*。推测执行的读操作走的仍是和其他所有读操作相同的[[page-table|页表]]。如果另一个站点的数据映射在渲染进程的地址空间里，推测执行就够得着；如果没有映射，就不存在任何通向它的虚拟地址，再怎么推测也造不出一个来。第 13 章的地址空间——每个进程都拥有自己内存的那个假象——原来是面对这类攻击时唯一守得住的边界。出于同样的原因，浏览器还降低了计时器精度、限制了 [[sharedarraybuffer|`SharedArrayBuffer`]]。这些措施只能让攻击变慢；把机密挪进另一个进程，才是让它彻底够不着。
:::

::scene site-isolation

于是 Chrome 换了隔离的单位。启用站点隔离后，每个渲染进程都被*锁定*到单一**站点**（site）的文档上。站点的定义是协议加上可注册域名，例如 `https://example.com`，连同它的所有子域名。之所以按站点而不是按[[origin|源]]（origin）划分，是因为同一站点下的页面仍可以通过设置 `document.domain` 变成同源，所以它们必须能共用一个进程。跨站 iframe 如今在自己的进程中渲染，称为进程外 iframe（out-of-process iframe）。浏览器把一个页面的各个框架从多个渲染进程中拼装起来，负责分发输入、合成它们的输出。

::scene corb

只隔离文档还不够，因为页面还可以去*抓取*别的站点的数据：恶意页面可以把 `https://bank.example/account.json` 当成图片或脚本来请求。浏览器会在网络响应到达渲染进程之前进行过滤：[[corb|跨源读取阻止]]（Cross-Origin Read Blocking，CORB）及其后继者 ORB，会阻止 HTML、XML、JSON 这类敏感类型的数据被送进一个锁定在其他站点上的进程。

下面的实验就是书中图 13.2 的动画版：三个进程，各自以为自己的内存从地址 0 开始，共享同一块物理内存。不妨把它们看成锁定在三个站点上的三个渲染进程。

::lab AddressSpace

可以试试这些：

- 选中进程 A，把它的虚拟地址从一头拖到另一头。它能构造出的每一个地址，都落在物理内存里属于 A 的那一段。这就是站点隔离承诺的全部内容：锁定在站点 A 上的渲染进程，不存在任何通往站点 B 数据的虚拟地址。
- 打开自动上下文切换。CPU 在进程之间轮转，但每个进程的地址转换也随之切换。一个进程崩溃，只是一个盒子里的崩溃。
- 留意实验*没有*展示的东西：共享的部分。GPU 进程和浏览器进程为所有渲染进程服务，持有来自许多站点的数据，所以发给它们的一切都要经过校验。

这个实验用的是第 15 章的基址/界限地址转换，比真实浏览器所依赖的分页简单。但隔离这一性质是一样的。

## 代价是什么

::scene cost

进程不是免费的。每个进程都有自己的[[page-table|页表]]和内核数据结构，它写过的内存都是自己的一份；在浏览器里，它还有自己的 JavaScript 堆，以及若干原本可以共享的缓存副本。站点隔离让进程数成倍增加，所以 Chrome 团队在发布之前先在真实用户身上测量了代价。

:::fold 站点隔离论文里的数字
Reis、Moshchuk 和 Oskov 在 USENIX Security 2019 的论文中，报告了来自 Chrome 桌面用户的这些数据：

- **进程数。** 中位数用户在没有站点隔离时有 4.4 个渲染进程，开启后是 6.2 个，增加 43.5%；在[[percentile|第 99 百分位]]，从 35.0 个增加到 52.7 个，增加 50.6%。中位数用户同时打开 6.0 个不同站点，第 99 百分位是 41.9 个。论文估计，如果每个站点的每个实例都单独占一个进程，第 99 百分位会达到 79.7 个进程；同站实例之间的进程共享让实际数量远低于此。
- **单进程内存。** 每个渲染进程要做的事变少了，所以也变小了：中位数下，单个渲染进程的私有内存下降 51.5%，从 87.2 MB 降到 42.3 MB。
- **总内存。** 把所有进程加起来，总私有内存在第 25 百分位增加 12.6%，在第 99 百分位增加 8.6%。“9%～13%”这个数字就出自这里。考虑到瞬态执行攻击的严重性，团队认为这个代价可以接受。
- **延迟。** 页面加载最多慢了 2.25%（第 25 百分位）。浏览器会预先保留一个**备用**渲染进程——已经启动、尚未锁定，随时可以分配给下一个要访问的站点——以此掩盖一部分进程启动时间。
- **微基准测试更难看。** 在干净的浏览器里单独加载某个站点时，一个需要 10 个进程的页面多用了 89% 的内存。真实用户会同时开着好几个标签页，进程共享因此有更大的腾挪空间。

在内存更紧张的 Android 上，Chrome 77 为内存不少于约 2 GB 的设备开启了部分站点隔离：只隔离用户登录过的站点。Chromium 项目 2019 年报告，这种配置的内存代价约为 3%～5%。
:::

论文最有价值的观察是：进程变多，并没有让内存按比例变多。站点隔离没有凭空制造新的工作，只是把同样的页面分给了更多、更小的进程。一个进程的固定开销——页表、内核状态、运行时的启动——确实存在，但远小于它所渲染的那些页面本身。

Chrome 也限制了进程数膨胀的程度。在桌面端，它根据机器内存设定一个软性的进程数上限。达到上限后，新文档会被放进已有的进程，但只会放进已经锁定在*同一*站点上的进程。在桌面端，站点隔离从不为了省内存而把两个站点放进同一个渲染进程。Android 上没有软上限：Chrome 依靠操作系统回收后台进程，就像手机回收后台应用一样，等你回到被丢弃的标签页时，浏览器再把它重建出来。

## 理想在哪里弯折

::scene bends

进程边界很坚固，但它不是故事的全部。

- **同一站点就是同一个[[principal|主体]]。** `example.com` 下的一切，包括用户托管的子域名，都可以共用一个进程。需要更细粒度隔离的站点可以请求**按源划分**（origin-keyed）的进程，而浏览器只把这个请求当作提示，而非保证。
- **并非所有平台都有。** 低内存的 Android 设备、Android WebView 和 iOS 版 Chrome 都没有站点隔离。在 Android 上，未被隔离的站点共用未锁定的进程，浏览器进程会额外检查，确保这些进程拿不到属于已隔离站点的数据。
- **内核仍是共享的。** 一个找到操作系统内核漏洞的渲染进程，可以一次性越过所有进程边界。这正是沙箱要收窄渲染进程可用系统调用的原因：调用越少，暴露的内核就越少。
- **高权限进程才是大奖。** 浏览器进程和 GPU 进程能看到所有站点的数据。控制了一个渲染进程的攻击者，会试着给它们发畸形消息。防御之道和操作系统守住系统调用边界的办法一样：检查跨过边界的一切。[这篇关于受限直接执行的笔记](/notes/lde-everywhere) 会展开讨论。

## 回到书里的那条线

::scene isolation

第 4 章引入进程，是为了让一个 CPU 看起来像很多个。浏览器用的是这个设计顺带白送的另一个性质：**隔离**。由硬件强制执行的私有地址空间，意味着一个程序无法读取或破坏另一个程序的内存；受限直接执行意味着唯一的出口是一扇由内核把守的门。浏览器在此之上叠加了自己的策略：决定哪个站点进哪个盒子，并且看好每一扇门。

其他浏览器也得出了同样的结论：Firefox 的 Fission 项目在 2021 年底的 Firefox 95 中为桌面用户上线了站点隔离。凡是运行不可信代码的地方，都能看到这个模式：把驱动挪进用户进程的[[microkernel|微内核]]，还有 [下一篇笔记](/notes/zombies-containers) 里的[[container|容器]]——它们用同一套内核机制，把整个应用装进盒子。而既然二选规则除了高权限之外，还把内存不安全的语言列为危险属性之一，长远的解决之道是从根本上消灭这些 bug，这是 [内存安全那篇笔记](/notes/memory-safety) 的主题。

关于浏览器吃内存的那个段子，其实有个严肃的答案：其中一部分内存，为你在银行和广告之间买下了一堵墙，而这堵墙就是第 4 章的进程。

## 延伸阅读

- Charles Reis、Alexander Moshchuk、Nasko Oskov：[*Site Isolation: Process Separation for Web Sites within the Browser*](https://usenix.org/system/files/sec19-reis.pdf)，USENIX Security 2019：设计、威胁模型，以及上文引用的测量数据。
- [Site Isolation](https://www.chromium.org/Home/chromium-security/site-isolation/)（Chromium 项目页面）：从桌面端 Chrome 67 到 Android 部分隔离的时间线，附内存数据。

- [Multi-process Architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/)（Chromium 设计文档）：最初的问题陈述。
- [Sandbox](https://github.com/chromium/chromium/blob/main/docs/design/sandbox.md) 与 [Linux sandboxing](https://github.com/chromium/chromium/blob/main/sandbox/linux/README.md)（Chromium 文档）：代理/目标模型、Windows 令牌与作业对象、命名空间与 seccomp-bpf。
- [The Rule of 2](https://github.com/chromium/chromium/blob/main/docs/security/rule-of-2.md)（Chromium 安全文档）。
- [The Linux zygote](https://github.com/chromium/chromium/blob/main/docs/linux/zygote.md)（Chromium 文档）：为什么渲染进程是 fork 出来的，而不是 exec 出来的。
- [Project Fission](https://wiki.mozilla.org/Project_Fission)（Mozilla wiki）：Firefox 的站点隔离项目。
