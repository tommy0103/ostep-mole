title: 大模型推理里的“护航效应”

::scene overview

想象你向聊天机器人发了一句话的问题，恰好同时有人让它写一篇 2000 个 [[llm-token|token]] 的长文。在一些早期的推理系统上，你那二十个 token 的回答要等长文写完才能回来。不是 [[gpu|GPU]] 太慢，而是两个请求被放进了同一批（batch），而这一批要一直跑到最长的那个请求结束。

2022 年，首尔大学和 FriendliAI 的一篇论文展示了这种做法的代价有多大。他们的系统 Orca 主要改变的是服务器*何时*做调度决策。在一个 [[model-parameters|1750 亿参数]]、GPT-3 规模的模型上，它在相同延迟下的吞吐量达到 NVIDIA [[fastertransformer|FasterTransformer]] 的 36.9 倍。这份提升有很大一部分，正是第 7 章里两种策略之间的差别。

这篇文章沿着第 7 章的顺序来看[[llm|大模型]]推理服务：FIFO 与护航效应，然后是抢占，然后是[[round-robin|时间片]]，最后是“无法预知”的问题——不知道一个任务要跑多久。

::scene workload

## 用第 7 章的语言描述工作负载

::chapter cpu-sched

[[transformer|Transformer]] 生成文本分两个阶段。在**预填充**（prefill）阶段，模型一次读完整个提示词，并行处理其中所有 token，产生第一个输出 token。在**解码**（decode）阶段，它一次一个地产生其余 token：每一步以上一个 token 为输入，每一步就是模型的一次*迭代*（iteration）。一个要生成 2000 个 token 的请求，需要一次预填充和大约 2000 次解码迭代。而这个数谁也无法事先知道：模型输出序列结束符时，生成才停止。

GPU 和书中的 CPU 还有一个重要区别。第 7 章的 CPU 一次运行一个任务；GPU 运行的是一**批**：一次迭代能让许多请求各前进一个 token。对解码来说，批处理几乎是免费的。每个解码步骤都要从内存里把模型权重读一遍，为每个请求产生一个 token；为 32 个请求读一次权重，并不比为 1 个请求读一次贵多少。Anyscale 团队 2023 年做测量时，把大模型推理描述为“[[memory-bound|受内存 I/O 限制]]，而不是受计算限制”。所以 GPU 不太像一个收银员，更像一辆公交车：吞吐量来自把座位坐满。

记住这个差别，术语就能和第 7 章紧密对应起来：

| 第 7 章 | 大模型推理服务 |
|---|---|
| 任务 | 请求 |
| 运行时间 | 提示词的预填充，加上每个输出 token 一次解码迭代 |
| 能否事先知道？ | 提示词长度能，输出长度不能 |
| 周转时间 | 端到端延迟 |
| [[response-time|响应时间]] | 首 token 时间（time to first token，TTFT） |
| 时间片 | 一次迭代：批中每个请求各一个 token |
| 上下文切换开销 | 抢占：请求的 KV 缓存被换出或重新计算 |

::scene kv

最后一行要解释一下。生成过程中，模型为每个请求维护一份 **KV 缓存**：迄今为止每个 token 的[[attention|注意力]]键和值，每个请求可以多达许多兆字节。暂停一个请求、稍后再恢复，就意味着得把这份缓存存在某处，或者重新算一遍。缓存在 GPU 内存里如何布局是[另一个故事](/notes/paged-attention)；这里它只作为抢占的代价出现。

::scene static

## 静态批处理：带座位的 FIFO

第一代推理系统以**整个请求**为单位调度。服务器凑好一批交给模型引擎，等其中每个请求都完成，才组下一批。Orca 的作者点出了由此带来的两个问题：提前完成的请求无法返回给客户端；批开始运行后才到达的请求，必须等这一批全部完成。

下面是一个以迭代为单位的简化例子：假设每次迭代耗时相同，忽略预填充。一批有四个座位。请求 A 要生成 2000 个 token；B、C、D 各生成 20 个。另一个 20 个 token 的请求 E 在这批刚开始后到达。

- **静态批处理。** 这批要跑 2000 次迭代。B、C、D 在第 20 次后就完成了，但它们的座位在剩下的 1980 次迭代里一直空着，答案要和 A 的一起返回。E 从第 2001 次迭代开始，到第 2020 次完成。平均完成时间：(2000 × 4 + 2020) / 5 ≈ 2004 次迭代。
- **每次迭代都重新决策。** B、C、D 在第 20 次迭代后离开，E 坐进空座，在第 40 次迭代完成；A 仍在第 2000 次完成。平均：(2000 + 20 + 20 + 20 + 40) / 5 = 420 次迭代。E 的第一个 token 在 21 次迭代后就到了，而不是 2001 次。

第一种调度就是书中的图 7.2，只是拧了一下。书里，B 和 C 排在 A 后面等 CPU；这里 B、C、D 甚至和 A 同用一块 GPU、早早干完了活，却还是得等。即便系统允许它们提前返回，E 依然要等到 A 结束。这就是**护航效应**：一些用资源很少的消费者，排在了一个重量级消费者后面。

::scene iteration

## 迭代级调度：Orca

Orca 的改动听起来很小：调度器每次只让引擎运行**一次迭代**，而不是一整个请求。每次迭代之后，它移除已完成的请求、返回其输出，并可以把等待中的请求加进批里。业界如今通常称之为*连续批处理*（continuous batching）。让它成为可能的是第二项技术——*选择性批处理*（selective batching）。同一次迭代里的请求可能处在截然不同的位置，有的在预填充，有的已经到了第 1500 个 token。于是 Orca 只对逐 token 进行的操作（比如那些大矩阵乘法）做批处理，而注意力则为每个请求单独计算。

这是书里的哪种策略？并不完全是 STCF，尽管很容易这么叫它。Orca 有意保持服务顺序：调度器按到达时间接纳请求，并保证论文所说的“迭代级先来先服务（FCFS）”性质——如果请求 *x* 比 *y* 先到，那么 *x* 运行过的迭代次数不少于 *y*。在批内部，每个请求每次迭代前进一个 token，所以这一批的行为像是时间片为一个 token 的轮转，只不过所有座位同时前进。

Orca 真正改变的是**抢占的粒度**。第 7 章里从 SJF 到 STCF 的关键一步，并不是更好的排序，而是允许调度器在新任务到达时重新决策，而不是只能等当前任务结束。迭代级调度让服务器拥有了这种能力，而且每个 token 一次。更好的排序可以在此基础上再加，后面几节会讲到。

效果很显著。Anyscale 2023 年在一块 40 GB 的 A100 上对 OPT-13B 做的基准测试显示：单是连续批处理，吞吐量就最多达到朴素静态批处理的 8 倍；再加上 [[vllm|vLLM]] 的内存管理，最多达到 23 倍。如今，迭代级调度已是 vLLM 和大多数其他推理系统的默认做法。

:::fold Orca 的接纳规则，以及它为什么预留了太多内存

::scene reserve

Orca 的算法 1 很短，下面是简化后的伪代码：

```py
# 伪代码，据 Orca 算法 1（OSDI 2022）简化
def select(pool, reserved, max_bs, n_slots):
    batch = []
    for req in sorted(pool, key=lambda r: r.arrival):   # 按 FCFS 顺序
        if len(batch) == max_bs:
            break
        if req.never_scheduled:                         # 首次调度：预留 KV 空间
            if reserved + req.max_tokens > n_slots:
                break
            reserved += req.max_tokens
        batch.append(req)
    return batch, reserved
```

有两个细节值得注意：

- 循环在第一个放不下的请求处就停止，而不是跳过它、去接纳排在后面的小请求。这保住了 FCFS 性质，也避免了[[starvation|饥饿]]；但这也意味着，一个预留量很大的请求会挡住它后面的所有人。
- 接纳时，Orca 按请求的**最大**输出长度 `max_tokens` 预留 KV 缓存空间，因为它不可能知道真实长度。一个 20 个 token 就停下的请求，占着按数千个 token 准备的预留。这就是第 15 章的[[base-bounds|基址/界限]]，连浪费都一模一样。用分页来解决它，正是 vLLM 的 PagedAttention 做的事，见 [PagedAttention 那篇](/notes/paged-attention)。浪费的内存少了，公交车上的座位就多了——那 23 倍里有很大一部分来自这里。
:::

## 在书里的模拟器上试试

下面的实验是第 7 章的调度器，不是大模型服务器，但其中的形态是相通的。

::lab Scheduler

- 载入 **护航效应**。任务 A（100）是那篇长文，B 和 C（各 10）是聊天回复。FIFO 的平均周转时间是 110；切到 SJF，降到 50。这是服务器如果知道输出长度就能拿到的收益。
- 载入 **晚到的短任务**。非抢占的 SJF 被困在 A 后面（103.33），就像 E 在批刚开始后到达的静态批处理；STCF 可以抢占，得到 50。这就是迭代级调度迈出的那一步。
- 切到时间片为 1 的 RR。响应时间变得极好，周转时间变差。别忘了实验里的 CPU 一次只跑一个任务；GPU 跑的是一批，所以只要批能装进内存，一个 token 的时间片对周转时间的伤害要小得多。

::scene stall

## 护航效应卷土重来：预填充

迭代级调度假定每次迭代都短且差不多长。解码迭代确实如此；预填充却不是：它要一口气处理整个提示词。Sarathi-Serve 论文（OSDI 2024）概括了两者的差别：预填充迭代“延迟高，但能让 GPU 计算饱和”，解码迭代则“延迟低，但计算利用率也低”。

于是设想一个服务器正在跑一批解码中的聊天请求，这时来了一个提示词很长的请求。如果调度器把它的整个预填充塞进下一次迭代，这次迭代就会长得多，批里的每个聊天请求都得等它。用户看到的，是流式输出的回答中途卡了一下。Sarathi-Serve 把这叫作*生成停顿*（generation stall）。这又是护航效应，只不过发生在一次迭代之内：一个重任务拖住许多轻任务。

::scene chunked

解决办法是第 7 章的下一个想法：时间片。**分块预填充**（chunked prefill）把一个长预填充切成大小大致相等的块，每次迭代只跑一块，与正在进行的解码一起执行。每次迭代有一个 token 预算：先安排解码，剩下的空间再给预填充块，这样新请求加入时不会让任何人停下。Sarathi-Serve 报告：在单块 A100 上，Mistral-7B 的服务能力是 vLLM 的 2.6 倍；在两块 A100 上，Yi-34B 最多 3.7 倍；在[[pipeline-parallelism|流水线并行]]下，Falcon-180B 最多 5.6 倍。

vLLM 现在的引擎也是这么做的。它的文档写道，分块预填充“只要可能就默认开启”。调度器先把所有待处理的解码请求排进批，再把剩余预算分给预填充。这个预算 `max_num_batched_tokens`，就是换了标签的第 7 章时间片两难：预算小，token 间延迟更好，因为拖慢每个解码步骤的预填充 token 更少；预算大，首 token 时间更好，因为新提示词能更快完成预填充。

::scene distserve

第二种办法是把两类工作彻底分开。DistServe（OSDI 2024）把预填充和解码放在**不同的 GPU** 上运行，再把 KV 缓存从一边交给另一边。这样每个资源池都能针对自己的阶段和自己的延迟目标来配置规模和并行方式：预填充看首 token 时间，解码看每个输出 token 的时间。论文报告，它最多能多服务 7.4 倍的请求，或满足严格 12.6 倍的延迟目标。这正是第 8 章[[mlfq|多级反馈队列]]的思路：一旦能分辨任务类型，就让它们排不同的队。

:::fold 为什么预填充和解码给 GPU 的负载如此不同
差别在于：从内存读入的每个字节，能支撑多少计算。

- **解码**时，每个请求每次迭代只贡献一个新 token。GPU 必须从内存读入模型的每一个权重矩阵，只为了乘上寥寥几个向量（每个请求一个）。每读一个字节只做很少的计算，于是内存带宽成了瓶颈。往批里多加请求，复用的是同一次权重读取——所以在别的资源耗尽之前，解码的批处理几乎是免费的。
- **预填充**时，一个请求一次贡献它全部的提示词 token。同样的权重读取，现在要乘上成千上万个向量。每个字节对应的计算量很高，GPU 的计算单元成了瓶颈。

对解码来说，通常最先耗尽的是存放 KV 缓存的内存。Anyscale 估计，一个 130 亿参数的模型每个 token 大约需要 1 MB 的状态。一个大批次里，每个请求几千个 token 的上下文，很快就能把一块 GPU 填满。这就是为什么在大模型推理里，“接纳谁”主要是个内存问题，也是为什么第 18 章的[[paging|分页]]思想最终搬上了 GPU。
:::

::scene oracle

## 无法预知：猜一个任务要跑多久

第 7 章最后处理的是它最难的那个假设：SJF 和 STCF 需要知道每个任务要运行多久，而真实的操作系统并不知道。大模型推理有一个“半个先知”：服务器确切知道提示词有多长，因此大致知道预填充的代价；但它不知道模型会生成多少个 token。

研究者把书里对这个问题的两种回答都试过了。

::scene mlfq

第一种是第 8 章的回答：让任务的行为暴露它的长度。FastServe（Wu 等，2023）以单个输出 token 为粒度抢占，并用一种**跳跃加入的多级反馈队列**（skip-join MLFQ）调度：请求不总是从最高优先级开始，而是按输入长度进入相应的队列，随着它不断生成而逐级下沉。生成得长的请求沉下去，新来的短请求先跑——这正是 MLFQ 对交互式任务的做法。作者报告，与 vLLM 相比，在相同平均延迟要求下吞吐量最多提高 31.4 倍，在相同[[tail-latency|尾延迟]]要求下最多 17.9 倍。

::scene predict

第二种回答是预测——第 8 章把它表述为“用过去预测未来”，[历史预测那篇](/notes/history-predicts)讲得更深：先估计长度，再按估计值执行 SJF。Fu 等（2024）注意到，精确的输出长度很难预测，但它们的*相对顺序*要容易些。他们训练一个模型，把一批请求按预期输出长度排序，然后让预测最短的先跑。他们报告：聊天服务的延迟降低到 1/2.8，合成数据生成的吞吐量提高 6.5 倍。

两者都继承了 SJF 的弱点：只要短请求源源不断，长请求就可能[[starvation|饿死]]。书里的办法在这里同样适用：MLFQ 的定期优先级提升、[[aging|老化]]（aging），或者在上面再加一层公平性机制，记录每个用户已经得到了多少 token。这套记账和 [EEVDF](/notes/eevdf) 的虚拟时间是同一个想法，只是单位换成了 token。

::scene bends

## 理想模型在哪里弯折

书里的模型能带你走出很远，但大模型推理在好几个地方打破了它：

- **处理器是一整批，而不是一个槽位。** 对一批请求做轮转，几乎不会拉长周转时间，书中 RR 的那份代价基本消失了。限制批的是内存，而不是时间。
- **每次迭代长短不一。** 书中的时间片是一段固定的时间；这里一次迭代的长度取决于里面装了什么。所以分块预填充限制的是每次迭代的 token 数，而不是时长。
- **抢占很昂贵。** 保存一个进程的寄存器只要几纳秒；一个被抢占请求的 KV 缓存却可能很大。vLLM 的 KV 缓存空间不够时，就会抢占请求；在它现在的引擎里，默认做法是丢弃这些请求的缓存，之后重新计算。文档提醒，这会损害端到端延迟。
- **有两个延迟目标。** 第 7 章在周转时间和响应时间之间权衡；大模型服务则要同时为首 token 时间和每个输出 token 的时间设定目标，两者把调度往不同方向拉。

::scene overview

## 回到书里的那条线

站得足够远看，大模型推理就是快进重放的第 7 章。请求级批处理是 FIFO，于是有了护航效应。迭代级调度补上了 STCF 相对 SJF 多出的那一样：在当前任务结束前重新决策的权力。分块预填充是时间片，它的 token 预算就是时间片长度的权衡。感知长度的调度器，则是在没有先知的情况下逼近 SJF 的尝试——靠 MLFQ 式的观察，或靠学来的预测。而这一切底下的内存，是第 18 章的[[paging|分页]]。

同样的教训，出现在任何大小悬殊的工作共用一条队列的地方，从 HTTP 到传输层协议——那是[队头阻塞那条线索](/notes/hol-blocking)的主题。书里用一句关于超市排队的话就讲清楚了；大模型服务器则是一个 token 一个 token 地重新学会了它。
